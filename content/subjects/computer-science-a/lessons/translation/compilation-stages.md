## Introduction

When the Python or Java compiler on a laptop in Bulawayo reports "missing bracket on line 12", it has done a great deal of work before saying so. It has read the characters, grouped them into words, checked that the words follow the rules of the language and only then started to build machine code. A compiler is not one step but a chain of stages, each with its own input, output and kind of error.

This lesson describes how an **interpreter** executes a program and the four stages of **compilation**: **lexical analysis**, **syntax analysis**, **code generation** and **optimisation**, each applied to a short statement. It finishes with how a compiler handles **recursion** using a stack. All outputs here were generated by code.

You should already know the difference between a compiler and an interpreter, and what a stack is.

## Key definitions

:::definition{term="Token"}
The smallest meaningful item of a program, such as a keyword, an identifier, a number or an operator, produced by lexical analysis.
:::

:::definition{term="Symbol table"}
A table, built by the compiler, that records each identifier (variable, constant, procedure) in the program together with information such as its type.
:::

:::definition{term="Parse tree"}
A tree, built by syntax analysis, that shows how a statement is made up from its parts according to the grammar of the language.
:::

:::definition{term="Intermediate code"}
Code in a simple form between the source code and the final machine code, which is independent of the processor and is easier to optimise.
:::

## How an interpreter works

An interpreter does not translate the whole program. It takes a statement, analyses it, executes it, and then takes the next one. If the statement is inside a loop it is analysed again each time it is reached, which is why interpreted programs run more slowly. No complete object code is produced, so the interpreter and the source code must both be available. Because the program is executed as far as the error, the statements before an error have already run.

## The four stages of compilation

| Stage | Input | Output | Errors found |
|:-:|:-:|:-:|:-:|
| Lexical analysis | Source code characters | Tokens and symbol table | Illegal characters, invalid names |
| Syntax analysis | Tokens | Parse tree | Statements that break the grammar |
| Code generation | Parse tree | Object code (or intermediate code) | – |
| Optimisation | Generated code | Faster or smaller code | – |

![The four stages of compilation: lexical analysis turns source code into tokens and a symbol table, syntax analysis builds a parse tree, code generation produces intermediate or object code, and optimisation makes it faster or smaller; errors are found in the first two stages](media:diagrams/translation-compilation-stages.png "Figure: the four compilation stages and what each one produces")

### 1. Lexical analysis

The lexical analyser reads the characters of the source code and groups them into **tokens**. It removes comments and white space (spaces and blank lines), which mean nothing to the processor, and it enters each identifier in the **symbol table**. The statement below has a comment, which is removed.

```
Cost ← Price * Qty + 15  // fee added
```

:::worked-solution{title="Tokens and the symbol table"}
| Token | Type |
|:-:|:-:|
| `Cost` | identifier |
| `←` | assignment |
| `Price` | identifier |
| `*` | operator |
| `Qty` | identifier |
| `+` | operator |
| `15` | number |

1. The comment `// fee added` and the extra spaces are removed.
2. The statement gives 7 tokens: three identifiers, one assignment symbol, two operators and one number.
3. Each identifier goes in the symbol table. Its type is added from the declarations:

| Identifier | Type (from DECLARE) | Use |
|:-:|:-:|:-:|
| Cost | REAL | variable assigned |
| Price | REAL | variable read |
| Qty | INTEGER | variable read |
:::

### 2. Syntax analysis

The syntax analyser checks that the tokens follow the **grammar** of the language and builds a **parse tree**. The tree shows the order in which the operators are applied, with operators of higher precedence lower in the tree. If the tokens break the rules, such as a missing bracket or `THEN` left out, the analyser reports a **syntax error** and compilation cannot continue.

![Parse tree of Price * Qty + 15: the root is + with children the * node and 15, and the * node has children Price and Qty, so multiplication (lower in the tree) is carried out before the addition](media:diagrams/translation-parse-tree.png "Figure: the parse tree for Price * Qty + 15")

:::worked-solution{title="Parse tree of Price * Qty + 15"}
```
+
    *
        Price
        Qty
    15
```

1. The multiplication has higher precedence, so it is lower in the tree and is carried out first.
2. The root is `+`, which adds the result of `Price * Qty` to 15.
3. Over the whole statement, an assignment node would join `Cost` to this tree.
:::

### 3. Code generation

The code generator walks through the tree and writes instructions. Many compilers produce **intermediate code** first, in which each instruction has at most one operator and the temporary results are given names.

```
T1 ← Price * Qty
T2 ← T1 + 15
Cost ← T2
```

Intermediate code does not depend on one processor, so it can be translated to machine code for several types of processor, and it is a convenient form to optimise.

### 4. Optimisation

The optimiser makes the code smaller or faster without changing what it does. Two common methods:

- **Constant folding:** an expression whose values are all known when compiling is worked out once by the compiler.
- **Removing redundant code:** code that can never be reached, or whose result is never used, is deleted.

:::worked-solution{title="Constant folding"}
```
Seconds ← 60 * 60 * 24
```

All three values are constants, so the compiler works out 60 × 60 × 24 = 86400 and generates:

```
Seconds ← 86400
```

The multiplications no longer need to be carried out every time the program runs.
:::

## Compiling recursion

A recursive subroutine calls itself, and each call needs its own parameters and local variables and a record of where to return. The compiler therefore generates code that uses a **stack**: a stack frame is pushed for each call and removed when it returns. The calls of `Fact(4)` build up to a depth of 4 and then unwind:

| Event | Stack depth after the event |
|:-:|:-:|
| call Fact(4) | 1 |
| call Fact(3) | 2 |
| call Fact(2) | 3 |
| call Fact(1) | 4 |
| returns 1 | 3 |
| returns 2 | 2 |
| returns 6 | 1 |
| returns 24 | 0 |

If the recursion never reaches its base case the stack becomes full and the program stops with a stack overflow.

## Common mistakes

:::mistake{title="Saying syntax analysis creates tokens"}
Tokens come from lexical analysis. Syntax analysis uses the tokens to build the parse tree.
:::

:::mistake{title="Saying optimisation changes what the program does"}
Optimisation changes how the code does it (faster or smaller); the result must stay the same.
:::

:::mistake{title="Saying an interpreter produces object code"}
It analyses and executes each statement directly; no complete translated copy is made.
:::

:::mistake{title="Confusing syntax errors with logic errors"}
The compiler finds syntax errors. A program that compiles can still give wrong results because of a logic error.
:::

:::exam-tip
Cambridge **Paper 3** asks you to **describe** each stage, in order, and to name the output of each: tokens and symbol table, parse tree, intermediate or object code, improved code. For a short statement, list its tokens or draw the parse tree as a table or indented list.
:::

:::exam-tip
"**Explain** how recursion is compiled": a stack is used to hold each call's parameters, local variables and return address; frames are pushed on a call and popped on return.
:::

## Summary

:::summary
- An interpreter analyses and executes one statement at a time and produces no object code.
- Lexical analysis removes comments and white space, produces tokens and builds the symbol table.
- Syntax analysis checks the grammar, builds the parse tree and reports syntax errors.
- Code generation produces (intermediate) code from the tree; optimisation improves it, for example by constant folding.
- Recursive calls are compiled using a stack of frames.
:::
